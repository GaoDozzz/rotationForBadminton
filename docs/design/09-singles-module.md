# 单打功能模块

版本：v1.1  
状态：已确认，纳入首版  
日期：2026-07-31

本模块将自由转从“仅双打”扩展为“球局级可选择单打或双打”。本文是对 v1.0 设计的增量规范；与既有文档中“每场固定 4 人、每队固定 2 人”的描述冲突时，以本文为准。

## 1. 产品规则

- 创建球局时必须选择比赛形式：`SINGLES`（单打）或 `DOUBLES`（双打）。
- 单打每场 2 人，1 对 1；双打每场 4 人，2 对 2。
- 同一球局首版只能使用一种比赛形式，不支持单打、双打混合排阵。
- 比赛形式可在生成首个赛程前修改；已有赛程后如需修改，必须废弃赛程并重新生成。
- 报名、正式/候补、代报名、取消截止、裁判、计分确认、比分修改、弃权、排名和临时退出重排规则保持一致。
- 单打最低 2 人可生成赛程；双打最低 4 人。
- 单打不计算搭档重复、混双搭档比例或队内水平差。
- 单打重点优化：上场次数均衡、减少重复对手、避免连续上场、避免连续休息和对手水平接近。

## 2. 单打积分和排名

积分仍等于比分差：

- 21:15 时，胜者 `+6`，败者 `-6`。
- 全体参赛者积分总和仍为 0。
- 同积分排序仍为：积分、胜场数、总得分、更少失分、并列。
- 11/15/21 分、领先两分、封顶分、弃权和比分确认规则与双打一致。

## 3. 性别规则

双打现有的“混双优先”和“禁止男双对女双”不适用于单打组队，单打采用对手性别策略：

- `ANY`：不限制对手性别。
- `PREFER_SAME_GENDER`：尽量安排同性别对手，人员结构不足时允许异性别对阵并给出提示。
- `REQUIRE_SAME_GENDER`：只允许同性别对阵；无解时阻止生成并说明原因。

兼容规则：若旧配置在单打下仅设置 `forbidMensVsWomens=true`，服务端映射为 `REQUIRE_SAME_GENDER`。

## 4. 页面变化

### 创建/编辑球局

- 在玩法下增加“比赛形式”单选：单打、双打。
- 选择单打后隐藏重复搭档、混双优先、禁止男双对女双等双打配置。
- 单打显示“对手性别”：不限、尽量同性、仅限同性。
- 人数校验、帮助文案和预估比赛数随比赛形式实时变化。

### 对阵和比赛详情

- 单打对阵卡片左右各显示 1 名球员；双打左右各显示 2 名球员。
- 使用同一组件的 `teamSize` 参数实现，不复制整套页面。
- 裁判区域、比分、场地、轮次和状态区域保持一致。

### 排名与复盘

- 单打隐藏搭档次数和搭档重复统计。
- 单打展示交手对手、交手次数、胜负和净比分。

## 5. 数据模型变更

### `events`

新增字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `match_format` | enum | `SINGLES/DOUBLES`，非空，默认 `DOUBLES` |

建议使用独立列而不是只放入 `settings`，便于查询、约束和后续统计。

`settings` 增加：

```json
{
  "opponentGenderPolicy": "ANY"
}
```

双打继续使用原有 `genderPolicy` 和 `forbidMensVsWomens`。服务端按 `match_format` 拒绝无意义或冲突的配置。

### `match_players`

- 单打：每侧只有 `slot_no=1`。
- 双打：每侧允许 `slot_no=1/2`。
- 由延迟约束或服务层事务校验每场总人数必须等于 `2 × teamSize`。
- `teamSize` 由所属球局的 `match_format` 推导，比赛记录不接受客户端单独修改。

### 快照

`schedule_versions.input_snapshot` 必须保存 `matchFormat`、`teamSize` 和对应性别策略，保证旧赛程可复现。

## 6. 接口变更

### 创建/修改球局

```json
{
  "playMode": "FREE_ROTATION",
  "matchFormat": "SINGLES"
}
```

- `POST /events` 接受 `matchFormat`，必填。
- `PATCH /events/:eventId` 只有在不存在赛程版本时允许修改 `matchFormat`。
- 球局详情、列表和分享卡片响应均返回 `matchFormat`。

### 生成赛程

`POST /events/:eventId/schedules/generate` 不允许客户端另传与球局不同的比赛形式；算法输入由服务端读取球局配置并加入：

```json
{
  "matchFormat": "SINGLES",
  "teamSize": 1,
  "playersPerMatch": 2,
  "constraints": {
    "opponentGenderPolicy": "PREFER_SAME_GENDER"
  }
}
```

### 响应能力

球局详情增加：

```json
{
  "capabilities": {
    "canChangeMatchFormat": true
  }
}
```

已有赛程时该值为 `false`。

## 7. 通用轮转算法

算法新增参数：

```ts
type MatchFormat = 'SINGLES' | 'DOUBLES';

interface RotationInput {
  matchFormat: MatchFormat;
  teamSize: 1 | 2;
  playersPerMatch: 2 | 4;
  // 其余字段沿用既有设计
}
```

`teamSize` 和 `playersPerMatch` 由服务端根据 `matchFormat` 推导，算法入口仍校验三者一致，避免错误调用。

### 场次数分配泛化

设参赛人数为 `N`、目标场次数为 `G`、每场人数为 `P`：

1. 理想总出场槽位为 `N × G`。
2. 比赛数 `M = round(N × G / P)`。
3. 实际总槽位为 `P × M`。
4. 将实际槽位平均分配给所有人，最大场次数差不得超过 1。

其中：

- 单打 `P=2`。
- 双打 `P=4`。

示例：5 人单打、每人目标 4 场，需 `5×4/2=10` 场，可精确满足。

### 通用硬约束

- 单打每场恰好 2 名不同参赛者，双方各 1 人。
- 双打每场恰好 4 名不同参赛者，双方各 2 人。
- 同一轮同一参赛者最多参加一场。
- 同一场地同一轮最多一场。
- 总场次数符合分配目标。
- 已退出/暂停人员不进入未来比赛。
- 已锁定比赛不可改变。
- 相应性别硬约束必须满足。

### 单打软目标

建议权重：

| 目标 | 权重 |
|---|---:|
| 场次数偏差 | 10000 |
| 重复对手 | `1000 × 超额次数²` |
| 连续上场 | `80 × 连续长度²` |
| 连续休息 | `70 × 连续长度²` |
| 场次时间分布不均 | 40 |
| 同性别偏好未满足 | 30 |
| 对手水平差 | 20 |

单打模式下搭档重复代价恒为 0，相关公平度字段返回 `null` 而不是误导性的 0。

### 公平度指标变化

通用指标保留总比赛数、轮数、最少/最多场次、最长连打、最长连休和总惩罚值。

单打增加：

- `repeatedOpponentPairs`
- `maxOpponentRepeat`
- `sameGenderMatchRatio`
- `opponentLevelImbalanceScore`

双打继续返回搭档相关指标。

## 8. 临时退出重排

单打重排流程与双打一致：冻结已完成和进行中的比赛，仅重排未开始比赛。区别仅在于每场补齐 2 人，并依据单打对手历史计算重复惩罚。

新增人员或恢复人员也必须先生成差异预览，由组织者确认后激活新赛程版本。

## 9. 单打测试与验收

- 2～32 人、1～8 个场地随机生成，单场始终恰好 2 人。
- 同轮同一球员不重复上场。
- 可精确平均时每人场次数相同；不可精确时最大差为 1。
- 相同输入、算法版本和随机种子产生相同结果。
- `REQUIRE_SAME_GENDER` 下不出现异性对阵；无解时返回明确原因。
- 单打比赛 21:15 后积分分别为 +6/-6，总积分为 0。
- 单打不返回搭档统计，不显示混双配置。
- 切换比赛形式后，创建页校验、预估比赛数和预览卡片立即正确更新。
- 重排后所有冻结的单打比赛完全不变。

## 10. 开发影响

新增工作包括通用算法改造、单打配置与页面适配、数据库迁移、接口字段和属性测试，预计增加 3～5 人日。

修订后的首版总工作量约 36～48 人日，单人开发预计 8～10 周。工程实现必须复用球局、比赛、计分和排名模块，不建立一套平行的“单打系统”。
